## 使用方式

1. 每次從下表指定項目編號開始，不把整份清單視為同時實作的授權。
2. 開工先取得最新 `main`，讀取 `README.md`、`AGENTS.md` 及對應程式；重新確認該問題仍存在。
3. 若已有使用者修改，保留修改並視需要使用獨立 worktree；不以 reset、覆寫或 force push 排除差異。
4. 沿用 `codex/<任務名稱>` 分支格式。確認缺陷用 `codex/bugfix-...`，改善、效能、工程與驗收使用各自前綴。
5. 每個 PR 說明處理的項目編號、變更、驗證結果及未完成事項；只調整與選定項目相關的範圍。
6. 修復後更新本檔狀態與末尾紀錄，保留原始問題與證據，不刪除歷史。
7. `CI 通過`、`已合併`、`已同步 gh-pages`、`公開站已驗證` 分開記錄，不互相替代。

優先度：P1 為正式對外推廣前應優先完善；P2 為下一輪改善或邊界補強；P3 為可排後的內容增補。優先度不代表所有項目都是程式缺陷。

狀態：`待處理` → `處理中` → `待驗收` → `已合併／待發布` → `已發布並驗證`。需要核定內容者使用 `待業務確認`，尚無實測結論者使用 `待驗證`。

## 條列內容與驗收條件

### XK-Q-001｜摘要完成後缺少正式洽詢承接

- **證據**：原始檢查中，公開頁的「查看 XK 聯絡資訊」可正常開啟，但目的頁仍顯示「正式聯絡管道確認中」。
- **影響**：沒有既有聯絡方式的新訪客，複製摘要後仍不知道可交給誰；這是正式推廣的業務承接缺口，不是外連失效。
- **相關位置**：`src/components/brief-tool.tsx`、`src/config/campaign.ts`；目的頁為 https://xk2022.github.io/xk-website/contact/ 。
- **處理方向**：先由 XK 確認可公開的正式管道，再調整「複製後下一步」說明；未核定前不自行新增 LINE、Email 或預約入口。
- **驗收**：首次接觸 XK 的訪客能知道摘要如何保存及交付；連結目的地存在且內容一致；草稿不附加到 URL，也不自動送出。
- **依賴**：官網與公司文件庫仍為唯讀參考。若需跨 repo 調整，由另行明確授權的工作處理。

### XK-Q-002｜部分小字文字對比不足

- **證據**：375px 本機同版靜態產物的 axe-core 4.14.1 掃描，`color-contrast` 指出 7 個節點：情境數字約 **3.52:1**、情境英文約 **3.73:1**（各三處）、示意手機 eyebrow 約 **4.48:1**。另有 7 處背景複雜而需人工判定。
- **補充**：來源色碼計算也指出 placeholder 在白底約 **3.54:1**。上述不是全站 WCAG 合格／不合格的完整結論。
- **相關位置**：`src/app/globals.css` 的 `.scenario-number`、`.scenario-english`、`.phone-eyebrow`、placeholder 等樣式；基準版約第 607、612、884 行附近，後續請以 selector 定位。
- **處理方向**：加深文字顏色，逐一確認實際背景；保留正式 Logo 原色與品牌幾何。
- **驗收**：相關一般小字在實際背景上的對比至少 **4.5:1**；以 375px／1440px 及人工檢視複核，對無法自動判定的項目留下結果，不宣稱只靠掃描即可通過全部 WCAG。

### XK-Q-003｜手機功能性說明字級偏小

- **證據**：375px 下，必填／選填及清空提醒約 **9px**、欄位說明約 **10px**、欄位標題約 **12px**；公開頁桌面計算樣式亦可見 9–10px 的輔助文字。
- **影響**：重要操作說明容易被忽略，對較小螢幕及閱讀能力不同的訪客較吃力；這是可讀性改善，不是宣稱 WCAG 規定了這些最小字級。
- **相關位置**：`src/app/globals.css` 的 `.field-meta`、`.field-help`、`.form-notice`、`.field-label` 與手機 media query。
- **處理方向**：優先放大功能性文字；可先評估約 14–16px，再依版面與實際閱讀核定。
- **驗收**：375／390px 能清楚閱讀必填、錯誤、隱私與清空說明；縮放文字後不遮擋、不截斷、不水平溢位；主要入口仍容易操作。

### XK-Q-004｜服務交付範圍說明不夠具體

- **證據**：頁面三個合作步驟主要描述「整理需求、確認頁面、預覽驗收」，對最終可規劃交付的內容仍較抽象。
- **影響**：訪客知道流程，但未必知道可討論哪些成果與後續維護方式。
- **相關位置**：`src/app/page.tsx` 合作方式區塊、`src/config/campaign.ts`。
- **處理方向**：由 XK 確認一段精簡的交付範圍，例如內容整理、手機版面、互動入口、驗收與交接；清楚區分已確認內容與需個案討論的項目。
- **驗收**：訪客能指出服務可討論的交付內容、自己應準備的素材及後續確認方式；不新增未核定的價格、固定交期、成效數字或客戶評價。

### XK-Q-005｜長摘要需要在文字框內另外捲動

- **證據**：375px 本機測量，示範摘要約 121 字時 `scrollHeight/clientHeight` 為 **328/328px**；加入約 318 字補充後為 **688/328px**，形成文字框內捲動。
- **影響**：全文核對較費力；目前沒有證據顯示複製會因此漏字，勿將閱讀改善寫成已確認的複製錯誤。
- **相關位置**：`src/components/brief-tool.tsx` 的 `summary-text`、`src/app/globals.css` 的 `.summary-text`。
- **處理方向**：評估自動增高或「展開全文」，保留可手動選取的全文。
- **驗收**：手機能看完長摘要；返回修改、再次產生與複製均使用最新全文；剪貼簿被拒時仍可完整手動選取；不引入草稿持久化。

### XK-Q-006｜零寬空白能通過必填驗證

- **證據**：`validateBrief` 目前以 `.trim()` 判斷；`"\u200b".trim().length === 1`。公開頁實際填入 U+200B 作為品牌、受眾及其他動作時可產生摘要，結果缺少可見資訊。
- **重現**：選「其他」主要動作，在三個必填文字欄分別只填入 U+200B，按「產生需求摘要」。
- **相關位置**：`src/lib/brief.ts` 的 `validateBrief`，基準版第 55–62 行；表單錯誤焦點位於 `src/components/brief-tool.tsx`。
- **處理方向**：檢查輸入是否具有有效可見內容，保留原始文字意思；不要任意刪除合法名稱、emoji 或文字中的連接字元。
- **驗收**：只有空白或不可見字元的必填文字被拒絕，錯誤顯示於對應欄位並聚焦第一個錯誤；合法中文、英文、emoji 與混合文字不被誤判；補必要的單元／元件回歸測試。

### XK-Q-007｜自由輸入完整句子與摘要套句銜接不自然

- **證據**：若「其他主要動作」輸入「我想讓客人下載型錄」，現有模板會產生「最希望訪客看完後我想讓客人下載型錄」。
- **影響**：摘要仍包含意思，但不如可直接轉貼的自然中文；屬文案／互動改善。
- **相關位置**：`src/lib/brief.ts` 的 `generateSummary`，基準版第 73–91 行；其他動作欄位提示。
- **處理方向**：先選定輸入提示或摘要模板策略，讓短語與完整句子都能保留原意；不默默代寫或改變使用者需求。
- **驗收**：「下載型錄」及「我想讓客人下載型錄」兩種輸入都能清楚呈現；返回修改後摘要及複製內容保持一致。

### XK-Q-008｜字型與 CSS 初載負擔值得量測及精簡

- **基準證據**：本機初載 31 個 WOFF2，ResourceTiming `encodedBodySize` 合計 **1,052,728 B**；本機伺服器無 HTTP 壓縮，該次 `decodedBodySize` 相同。CSS 檔案約 **370,561 B**，其中 `@font-face` 宣告占約 **92.4%**。
- **界線**：這不是公開站的網路 transfer、Core Web Vitals 或真實使用者體驗資料；磁碟上全部字型約 16.5MB，也不等於每位訪客下載量。尚不能判定某個載入指標不合格。
- **相關位置**：`src/app/globals.css` 的 Fontsource imports、`package.json`、輸出的 CSS／字型。
- **處理方向**：先固定裝置、快取及網路條件建立量測基準，再評估字重、字集、宣告與備援字型；不為減小檔案犧牲正體中文與使用者輸入的字形覆蓋。
- **驗收**：留下可比較的前後量測條件及結果，檢查字型請求、文字顯示及版面位移；保留品牌字體決策，確認改善後再訂出具體效能結論。

### XK-Q-009｜Pages 發布設定、文件與版本核對不一致

- **原始檢查證據**：README 採 `gh-pages` 分支發布；CI 名為 `Verify GitHub Pages export`，只保存產物、沒有 deploy job。但 Pages API 回傳 `build_type: workflow`，同時 `source` 欄保留 `gh-pages` 與 `/`。不能只看 source 欄就認定分支發布已啟用。
- **影響**：可能出現 main 的 CI 成功、產物已保存，但公開網站尚未更新的混淆。手動發布本身不是缺陷。
- **相關位置**：`.github/workflows/pages.yml`、README、GitHub Settings → Pages；公開資訊 API：https://api.github.com/repos/xk2022/xk-campaign-website-design/pages 。
- **處理方向**：開工重新讀取實際設定，確認採用的發布模式，再使設定、workflow 與文件一致；產物應能對照來源 SHA、`gh-pages` 成品 commit 與公開站。
- **驗收**：來源模式確實符合核定流程；保存來源／產物／發布紀錄，並在公開站核對首頁、品牌資產、索引 metadata 與主要摘要操作。管理 API 若為 403，記錄必要管理步驟，不宣稱設定已修改；不自行改變 repo 可見性。
- **注意**：設定可能在原始檢查後已變更，本項不是 2026-11-23 的即時設定斷言。

### XK-Q-010｜製造與活動情境的成果示意可補強

- **觀察**：目前首屏手機示意偏在地店家；製造與活動訪客主要依文字想像成果。
- **處理方向**：先核定是否加入精簡的情境示意或已核對的自主展示；不用硬放多張作品卡。
- **驗收**：不同情境訪客能理解可呈現的內容與主要動作；示意畫面明示性質，具名素材核對來源，不宣稱為付費客戶或交付實績。

### XK-Q-011｜實體手機、Safari 與 LINE 內建瀏覽器待驗證

- **證據界線**：已完成的是指定 viewport 的 Chromium 驗收；不能推論實體手機、Safari 或 LINE 內建瀏覽器已通過。
- **處理方向**：在可用的實體 iPhone／Android 及 LINE 內建瀏覽器檢查首屏入口、鍵盤、表單焦點、剪貼簿與外連返回。
- **驗收**：記錄裝置、OS、瀏覽器／LINE 版本與日期；走完情境選取、草稿保留、摘要修改、複製成功／拒絕與手動複製、外連及重新整理清空。無法取得的環境標示未驗證，不標為已修復。

- **業務待確認**。XK-Q-001／004／010 先取得核定內容；不得把公司官網或聯絡管道當成本專案可自行修改的範圍。
- **量測與維運**。XK-Q-008 先量測再優化；XK-Q-009 先重新核對設定；XK-Q-011 依可取得的裝置執行。

後續可直接給 Codex 的任務格式：


上例是後續任務範本，**不是本次開始修復或新增發布授權**。每次依使用者指定的範圍調整交付方式。

## 共通驗收與保留事項

- 功能修復依範圍執行 `npm run lint`、`npm run typecheck`、相關單元測試、建置及 Pages 子路徑驗收；完整交付依既有 CI 與 README 執行。純文件更新檢查連結、編號、日期與差異，不把舊測試結果當成本次新驗證。
- 涉及版面時核對 375、390、768、1024、1280、1440px、鍵盤焦點、長文字與無水平溢位；涉及剪貼簿時核對成功、拒絕及手動全文選取。
- 既有規格保留：草稿僅在記憶體、重新整理清空；未核定前維持 `noindex, nofollow`；不自行新增價格、固定交期、成效數字、評價或聯絡管道。
- 先前已加入的剪貼簿版本 guard、情境切換保留草稿與錯誤焦點不重新列為已知 bug；修改時需避免回歸。
- 主要按鈕、情境入口與素材標籤已有可操作的點擊區；較小的頁尾／次要入口可另評估放大，不直接宣稱它們已違反 WCAG target-size。
